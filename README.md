# AI Developer Package — How to Use

## What this is
Everything an AI developer (Claude Code) needs to build the UAE Policy Sales Portal, run UAT, and prove launch-readiness — without inventing requirements or losing its place between sessions.

## Repo layout to create
```
policy-sales-portal/
├── CLAUDE.md                  ← master brief (this package)
├── PROGRESS.md                ← living tracker (this package)
├── docs/
│   ├── requirements/          ← copy ALL WP files here (WP-00 … WP-13) — the law
│   └── build/
│       ├── ARCHITECTURE.md    ← this package
│       ├── BUILD-PLAN.md      ← this package
│       ├── UAT-PLAN.md        ← this package
│       ├── RELEASE-READINESS.md ← this package
│       └── CONFIG-REGISTER.md ← generated by the developer at M0-T4
├── src/ …                     ← created by the developer
└── uat/ …                     ← created by the developer (auto specs + manual scripts)
```

## Kickoff prompt (paste to Claude Code in the repo root)
> Read CLAUDE.md fully, then PROGRESS.md, then docs/build/BUILD-PLAN.md. Confirm your understanding of the source-of-truth hierarchy and the two human gates in one short summary. Then begin M0-T1. Follow the session protocol in CLAUDE.md §3 exactly.

## Your job as product owner (the parts AI cannot do)
1. **Answer "Blocked" items in PROGRESS.md promptly** — placeholder values, credentials, decisions.
2. **Hold the two gates.** GATE-1: play with the mock-mode engine yourself across all three regimes before approving. GATE-2: read the UAT report, not just the summary line.
3. **Feed real-world inputs when they arrive:** signed insurer annex (rates, loading lists, forms), ICP/goAML/MOHRE credentials, WhatsApp template approvals.
4. **Never edit code to change behaviour** — change the WP document, log it in WP-00's decision log, and let the developer implement from the amended spec. The traceability chain only works one direction.

## Why this structure works
- WP suite = immutable spec → the AI can't drift.
- Session-sized tasks + PROGRESS.md → token/context exhaustion never loses work.
- Rule-ID traceability (spec → code → test → UAT scenario → sign-off) → "done" is provable.
- Mock-first adapters → the whole product is testable before any external party grants access.
- PLACEHOLDER_ startup guard → the system physically cannot launch half-configured.
